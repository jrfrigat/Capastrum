## Граф пакетов

```text
Capastrum.JsonRpc
├── Capastrum.Mcp.Protocol ── Capastrum.Mcp
│                          └─ Capastrum.Mcp.Client
└── Capastrum.Acp.Protocol ── Capastrum.Acp
                           └─ Capastrum.Acp.Server
```

Граф представляет собой дерево с одним общим корнем. Пакет ссылается только на то, что находится непосредственно под ним, а MCP никогда не ссылается на ACP или наоборот. Приложение может взять одну ветвь, обе или один лист, не неся остальное.

| Слой | Отвечает за | Не отвечает за |
| :-- | :-- | :-- |
| `Capastrum.JsonRpc` | Конверт, идентификаторы, сопоставление запросов, транспорты, кадрирование потока | Методы протоколов, схемы, время жизни процессов |
| `*.Protocol` | Типизированные записи, перечисления, имена методов и уведомлений, сериализаторы | Транспорт, диспетчеризацию, поведение приложения |
| `Capastrum.Mcp` / `.Client` | Диспетчеризацию MCP, регистрацию, discovery, MRTR, подписки | Хостинг, DI, логирование, конфигурацию |
| `Capastrum.Acp` / `.Server` | Поведение ACP-хоста и агента, разрешения, файлы, терминалы | UI редактора, логику агента, политику рабочего пространства |

## Слои протоколов

### JSON-RPC

Ядро знает три формы сообщений и один peer. Оно сопоставляет ответы по `JsonRpcId`, передаёт входящие запросы единственному обработчику и поднимает уведомления подписчикам. Всё, что относится к конкретному протоколу, остаётся снаружи: уведомления об отмене, диапазоны кодов ошибок и формы параметров принадлежат слою выше.

`IJsonRpcTransport` намеренно мал: `SendAsync` и `ReadAsync` над `JsonRpcMessage`. Поэтому транспорты newline, WebSocket и HTTP можно менять, не затрагивая peer и протокольный код.

### MCP

MCP - протокол запросов и ответов без состояния с инициируемым сервером вводом. Сервер представляет собой реестр инструментов, ресурсов, шаблонов ресурсов и промптов; каждый запрос диспетчеризуется по этому реестру с контекстом на время запроса.

Ключевые решения:

- `server/discover` - единственное место, где клиент узнаёт идентичность сервера, возможности и поддерживаемые версии.
- Версия протокола и возможности клиента передаются в `_meta` каждого запроса, поэтому серверу не нужен рукопожатие с состоянием соединения.
- `resultType` отличает окончательный результат от результата `input_required`.
- Состояние MRTR непрозрачно для протокольного слоя. Сервер возвращает `requestState`; клиент возвращает его без изменений вместе с `inputResponses`.
- Подписки - это объекты фильтров, привязанные к потоку `subscriptions/listen`; уведомления маршрутизируются по этим фильтрам, а не рассылаются каждому соединению.

HTTP-поверхность не зависит от транспорта. `HandleHttpRequestAsync` принимает `McpHttpRequest` и возвращает `McpHttpResponse`, поэтому ASP.NET Core, minimal API или собственный сервер могут разместить его без зависимости Capastrum от веб-фреймворка.

### ACP

ACP - протокол хоста и агента с долгоживущим соединением. Хост запускает агента и отвечает на его исходящие запросы: разрешения, чтение и запись файлов, терминалы, elicitation.

Ключевые решения:

- Процессом владеет хост. `AcpAgentClient.StartAsync` запускает его, подключает stdio и выполняет `initialize` до возврата.
- Разрешения запрещены по умолчанию. Без `OnActionConfirm` каждый `session/request_permission` получает отказ.
- Доступ к файловой системе явный. Отсутствующий обработчик чтения или записи даёт ошибку «метод не найден», а не неограниченный доступ.
- Терминалами управляет `AcpTerminalHost`: он владеет временем жизни процессов, буферизованным выводом и лимитом вывода.
- Состояние сессии принадлежит приложению. Сервер агента маршрутизирует запросы и ходы промптов, но не навязывает хранилище сессий.
- Отмена кооперативная: `session/cancel` отменяет токен промпта, а агент возвращает причину остановки `cancelled`.

## Контракты и сериализация

Каждый проводной тип - запись или перечисление в протокольном пакете. Source generation `System.Text.Json` создаёт метаданные для запросов, результатов, уведомлений и конверта JSON-RPC. Ни один протокольный путь не откатывается к рефлексивной сериализации.

Данные, определяемые приложением, остаются `JsonElement`:

- аргументы инструментов и структурированное содержимое;
- JSON-схемы инструментов и elicitation;
- `rawInput` и `rawOutput` в ACP;
- payload расширений.

Это намеренная граница: протокол типизирует то, что типизирует спецификация, а приложение сохраняет владение формами, которые понимает только оно.

Контексты сериализаторов публичны, поэтому вызывающий код может составлять типизированные вызовы без собственных метаданных:

```csharp
var result = await peer.InvokeAsync(
    McpProtocol.Methods.ListTools,
    parameters: null,
    McpJsonContext.Default.McpListToolsResult);
```

## Асинхронность и время жизни

- Весь ввод-вывод асинхронный и принимает `CancellationToken`.
- `JsonRpcPeer` владеет одним циклом чтения и одной таблицей ожидающих запросов.
- Серверы и клиенты реализуют `IAsyncDisposable`; освобождение завершает ожидающие вызовы и освобождает транспорты или дочерние процессы.
- Клиент stdio уничтожает дерево дочерних процессов, если установка соединения не удалась.
- Хосты не создают контейнер DI, логгер или систему конфигурации. Их объекты параметров - обычные классы со свойствами `init`.

## Тестирование

В репозитории шесть тестовых проектов:

| Проект | Что проверяет |
| :-- | :-- |
| `Capastrum.JsonRpc.Tests` | Конверт, peer, транспорты, ошибки |
| `Capastrum.Mcp.Tests` | Диспетчеризацию сервера, регистрацию, MRTR, HTTP |
| `Capastrum.Mcp.Client.Tests` | Discovery, вызовы, уведомления, обработчики |
| `Capastrum.Acp.Tests` | Разрешения хоста, файлы, терминалы, сессии |
| `Capastrum.Acp.Server.Tests` | Диспетчеризацию агента, ходы промптов, отмену |
| `Capastrum.Conformance.Tests` | Поверхность протоколов и сквозную межпротокольную цепочку |

Conformance-проект проверяет, что каждый объявленный метод реализован, а путь ACP-хост -> агент -> MCP-клиент -> MCP-сервер работает как единая система.

`benchmarks/Capastrum.Benchmarks` замеряет сериализацию конверта JSON-RPC, полный круговой запрос peer в памяти и диспетчеризацию инструментов MCP.

## Ограничения

- **Сначала .NET 10.** Репозиторий нацелен на `net10.0` и использует возможности C# 13/14, доступные там. Другие целевые платформы допустимы, только если не замедляют сборку для .NET 10.
- **Никакой привязки к фреймворку.** Capastrum - набор библиотек, а не прикладной фреймворк. Он не требует конкретного хоста, контейнера DI или абстракции логирования.
- **Независимые пакеты.** У каждого пакета собственное описание, зависимости и идентичность в NuGet; общего пакета-зонтика нет.
- **Предупреждения - ошибки.** Сборка включает nullable-анализ, анализаторы и генерацию документации.
- **Документация публичного API обязательна.** Каждый публичный тип и член несёт `<summary>`; комментарии объясняют решения, а не синтаксис.
